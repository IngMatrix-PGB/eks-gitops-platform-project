# ADR-0011: Terraform foundation

**Status:** Accepted
**Date:** 2026-09-05

## Context

Phase 2.7 moves this project from the local `kind` lab toward a real
Amazon EKS platform, per the canonical plan
(`.local/evidence/phase-2.7-eks-aws-foundation-plan.md`). That plan was
split into five bounded subphases (2.7.1–2.7.5) because they differ
materially in what they touch (toolchain vs. networking vs. identity vs.
GitOps overlay vs. operations documentation) and, critically, in whether
they contact AWS at all. This ADR covers only **2.7.1 — Terraform
Toolchain and Offline Validation**: establishing a pinned Terraform CLI
and AWS provider, and the entire offline validation pipeline
(`terraform fmt`, `terraform init -backend=false`, `terraform validate`,
`terraform test` with `mock_provider`), with **zero** Terraform resource
code describing real infrastructure.

The user's authorized budget for Phase 2.7 is **exactly USD 0**, and no
AWS account exists for this project yet. This is not a soft preference —
it is a binding constraint that shapes every decision below. Every
capability this ADR adopts had to be verified, before adoption, as
achievable with no AWS credentials, no AWS account, no AWS network
contact of any kind, and no cost.

## Decision

**Terraform CLI `1.16.1`** and **AWS provider `hashicorp/aws` `6.63.0`**
are pinned in `terraform/versions.tf`, both confirmed as the current
latest stable releases directly against `releases.hashicorp.com` and the
Terraform Registry API on 2026-09-05 (`registry.terraform.io/v1/providers/
hashicorp/aws/versions` confirms `6.63.0` present among stable releases).
Re-verify both at actual infrastructure-authoring time (2.7.2+) rather
than trusting this ADR's dated snapshot indefinitely.

**Terraform is distributed and installed exactly like every other
project-local tool** (`kind`, `kubectl`, `helm`): a pinned row in
`scripts/lab/tool-versions.txt` (one per supported platform,
`darwin-arm64` and `linux-amd64`), downloaded and checksum-verified by
`scripts/lab/install-tools.sh` into `.tools/bin/terraform`, never
installed globally, never via a GitHub Action. Both the
`download_sha256` (of the `.zip` as downloaded) and `installed_sha256`
(of the extracted `terraform` binary) were verified directly against
`releases.hashicorp.com/terraform/1.16.1/terraform_1.16.1_SHA256SUMS`
and by extracting and hashing the actual binary — not invented, not
copied from a third party.

Terraform ships as a `.zip`, which `install-tools.sh` did not previously
support (only `raw` and `tar.gz`). A new `extract_pinned_member_zip()`
function was added, mirroring the existing `tar.gz` extraction
function's exact safety contract: the full archive inventory is
inspected before any extraction is attempted (rejecting the whole
archive if any entry is an absolute path or contains a `..` traversal
segment); the requested member must appear exactly once; extraction
targets only that one named member, never the whole archive; the
extracted result is rejected if it is a symlink or not a regular file;
the extracted path is confirmed to remain inside the temporary
directory (zip-slip defense); the checksum is verified before an atomic
`mv`; and cleanup runs via the existing `trap ... EXIT INT TERM` on the
shared `mktemp -d` scratch directory. An archive carrying an unrelated
extra member (Terraform's own release zip also contains `LICENSE.txt`)
is handled correctly — only the named member is ever extracted.

**`.terraform.lock.hcl` is generated by `terraform providers lock
-platform=darwin_arm64 -platform=linux_amd64`**, run against the real,
pinned, checksum-verified `.tools/bin/terraform` binary — never hand-
written — and committed, carrying `h1:`/`zh:` checksums for both
supported platforms so `terraform init` never needs to re-derive them.

**`terraform test` with `mock_provider "aws"` is the chosen mechanism
for proving Terraform logic offline**, in preference to any workaround
involving real (or fabricated) AWS credentials with a validation flag
that merely suppresses the credential check. This was verified,
against official HashiCorp documentation, to genuinely require zero AWS
credentials, zero provider configuration, and zero network contact to
AWS in both `plan`- and `apply`-mode `run` blocks (`developer.hashicorp.
com/terraform/language/tests/mocking`) — confirmed empirically in this
implementation as well, by running the test suite with
`AWS_SHARED_CREDENTIALS_FILE=/dev/null`, `AWS_CONFIG_FILE=/dev/null`,
and `AWS_EC2_METADATA_DISABLED=true` and observing identical passing
results. A minimal fixture (`terraform/main.tf` +
`terraform/tests/toolchain.tftest.hcl`) proves this mechanism works —
two inert, read-only AWS data sources (`aws_caller_identity`,
`aws_region`) and a validated input variable, entirely mocked — without
describing any project infrastructure (no VPC, EKS, IAM, or Secrets
Manager resource appears anywhere in this subphase).

**CI (`validate.yml`) gains exactly one new step** running `make
terraform-validate-offline` after the existing `make tools-install`
step (which now also downloads the pinned Terraform binary via the same
checksum-verified pipeline as every other tool). No new Action is added
— `hashicorp/setup-terraform` is deliberately **not** adopted, since it
is neither GitHub-owned nor already present in this repository's
`selected-actions` allow-list (`github_owned_allowed: true,
verified_allowed: false, patterns_allowed: []`, per ADR-0009), and
changing that GitHub-side setting is out of scope for this ADR. The new
step requests no new permission (`id-token: write` is never added), no
AWS secret or variable is referenced, and no `aws-actions/*` action or
AWS login step exists anywhere in the workflow.

## Alternatives Considered

- **`hashicorp/setup-terraform` GitHub Action**: rejected for this
  subphase — it would require expanding the repository's Actions
  `selected-actions` allow-list, a GitHub settings change explicitly out
  of scope here (Phase 2.7's own binding constraints forbid changing
  GitHub settings). The checksum-verified download script achieves the
  same outcome with zero policy change and reuses an already-proven
  pattern.
- **A real `terraform plan`/`apply` against AWS, gated by fake or
  disabled credential validation (e.g. `skip_credentials_validation`
  with placeholder keys)**: rejected outright — this would produce a
  misleading appearance of real validation while still risking an
  actual AWS API call (STS, IMDS, or otherwise) depending on provider
  version behavior, and is explicitly prohibited by this phase's own
  binding constraints.
- **LocalStack to simulate EKS/AWS APIs**: rejected — explicitly
  prohibited by this phase's binding constraints, and would not
  meaningfully validate real AWS behavior regardless.
- **Skipping `terraform test` entirely, relying only on `fmt`/
  `validate`**: rejected — `validate` only confirms syntax and internal
  consistency, not logical correctness (e.g., a variable validation
  rule actually rejecting bad input); `mock_provider`-based testing
  closes that gap at zero cost and zero AWS contact.
- **Deferring the ZIP-extraction safety work and just calling `unzip`
  without inventory inspection**: rejected — every other archive format
  this toolchain already supports (`tar.gz`) is defended against path
  traversal/symlink/multi-entry archives; a lower bar for `.zip` would
  be an inconsistent, unjustified regression in the toolchain's own
  security posture.

## Consequences

### Positive

- The entire Phase 2.7.1 surface is provably free: no AWS account,
  credential, or network contact is required to install the toolchain
  or run every validation this ADR describes.
- `terraform test`/`mock_provider` closes a real gap (logical/precondition
  correctness) that `fmt`/`validate` alone cannot — before any real
  infrastructure code exists to test.
- Terraform now follows the exact same pinned, checksum-verified,
  `.tools/bin/`-scoped installation discipline as every other tool in
  this project, rather than introducing a second installation
  mechanism.

### Negative

- `mock_provider`'s default computed-value fidelity is low; any future
  subphase whose logic depends on realistic computed values (ARNs,
  IDs) must supply explicit `mock_resource`/`override_resource` blocks
  — an ongoing authoring cost, not a one-time one.
- The ZIP-extraction function duplicates most of the tar.gz function's
  logic rather than sharing it, since the two formats' pre-extraction
  inventory mechanisms differ enough (`tar tvzf`'s verbose type field
  vs. `unzip -Z1`'s plain-name listing) that a shared implementation
  would need to abstract over that difference; accepted as a
  deliberate, readable duplication over a premature abstraction.
- A `mock_provider`-only test suite proves logical correctness, never
  real-AWS success (quota limits, IAM propagation delays,
  region-specific availability remain unverifiable until a real
  account exists) — an explicitly named, not hidden, limitation.

## Security and Cost Implications

Zero cost: no AWS resource is created, no AWS account is contacted, no
billable API call of any kind occurs. Security posture: no new GitHub
Actions permission, secret, or third-party Action is introduced; the
Terraform provider plugin download during `init`/`validate`/`test` only
ever contacts the public Terraform Registry, never an AWS endpoint,
confirmed both by official documentation (`terraform validate` "does
not validate... provider APIs") and by this implementation's own
explicit test with AWS credentials/metadata forcibly nulled. The
ZIP-extraction path applies the same path-traversal/symlink/multi-entry
defenses already proven for `tar.gz`, so the toolchain's security bar is
not lowered by adding a new archive format.

## Validation Method

`make terraform-validate-offline` (`terraform fmt -check` +
`terraform init -backend=false` + `terraform validate` + `terraform
test`) run against a real, checksum-verified `.tools/bin/terraform`
binary, twice (to confirm a second `make tools-install` is a true
no-op), plus an explicit run with `AWS_SHARED_CREDENTIALS_FILE=/dev/
null`, `AWS_CONFIG_FILE=/dev/null`, and `AWS_EC2_METADATA_DISABLED=true`
confirming identical results with AWS credential/metadata resolution
forcibly disabled; `tests/lab/test-tool-platforms.sh`'s new ZIP-specific
regression cases (correct platform selection, download-checksum
mismatch, installed-checksum mismatch, path traversal, absolute path,
symlink rejection, an extra unrelated archive member, a non-executable
binary, and an unsupported platform) proving `extract_pinned_member_zip`
fails closed on every unsafe input; `make validate`, `git diff --check`,
and a secrets scan confirming no AWS account ID, role ARN, or credential
material appears anywhere in this subphase's files.
